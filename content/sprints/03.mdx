## 0. Por que este Sprint existe

Até agora seu harness governa **um agente** trabalhando **uma tarefa por vez** num ambiente controlado. Funciona bem em demo. Em produção, isso quebra em 3 cenários simultâneos:

1. **Vários agentes trabalhando em paralelo** (ex: Codex orquestrando 12 features ao mesmo tempo).
2. **Mensagens chegando da internet** (WhatsApp, Slack, GitHub) que você precisa receber sem perder e sem deixar o servidor cair sob carga.
3. **APIs externas falhando** intermitentemente (rate limit, timeout, indisponibilidade) sem queimar dinheiro em retries cegos.

O Sprint 3 ensina os **3 padrões de borda** que separam um sistema agêntico de brinquedo de um sistema em produção.

## 1. Os 3 conceitos-âncora

### 1.1 Webhook desacoplado

<Aviso variante="dica" titulo="Antes de tudo, o que é 'webhook'?">
"Webhook" = "gancho web". É uma URL no seu servidor que **outros sistemas chamam quando algo acontece**. Ex: alguém manda mensagem no WhatsApp → Meta envia um POST HTTP pro seu webhook avisando.

Diferente de você ficar consultando ("ei, chegou mensagem? ei, chegou mensagem?" a cada 5s), webhook é o outro lado **te avisar** quando acontece.
</Aviso>

Provedores como Meta dão até **4 segundos** para você responder `200 OK`. Seu agente leva 5–30s para processar. Se você processa **inline**, o webhook timeouta → Meta re-envia → você processa **de novo** → loop infinito gastando dinheiro.

A regra é:
1. Webhook **valida e enfileira** (rápido).
2. Worker **consome a fila** (devagar, tudo bem).

<Aviso variante="dica" titulo="Antes de tudo, o que é 'HMAC-SHA256'?">
HMAC = "Hash-based Message Authentication Code". SHA-256 é um tipo de "função picotadora" (hash). Juntos: **carimbo digital que prova quem mandou e que ninguém alterou no caminho.**

Analogia: imagine que você combina uma SENHA com seu amigo. Toda carta que você manda, você calcula um número mágico usando (texto da carta + senha) e escreve no fim. O amigo recalcula com a mesma senha + texto recebido. Se bater, foi você. Se não bater, foi adulterada.

Em código, é só uma linha: `crypto.createHmac('sha256', segredo).update(payload).digest('hex')`. Você não precisa entender a matemática.
</Aviso>

Para validar quem mandou, usa-se **HMAC-SHA256**: provedor assina o payload com chave secreta, você recalcula e compara. Mas **em tempo constante** — comparar string normal vaza informação sobre quantos caracteres bateram (timing attack).

### 1.2 Erros transientes vs permanentes

<Aviso variante="dica" titulo="Antes de tudo, o que são códigos HTTP?">
Quando você chama uma API, ela responde com um número de 3 dígitos:
- **2xx** = deu certo (`200 OK`, `201 Created`)
- **3xx** = redireciona
- **4xx** = você errou na requisição (`404 não existe`, `401 sem autenticação`)
- **5xx** = o servidor errou (`500 erro interno`, `503 indisponível`)

Decorar TODOS é overkill. Decore os 5 abaixo:
- `200` = OK
- `401` = sua chave está errada
- `404` = recurso não existe
- `429` = você está chamando MUITO rápido (rate limit)
- `500/503` = servidor com problema
</Aviso>

| Erro | Tipo | O que fazer |
|---|---|---|
| `408 Timeout` | Transiente | Retenta com backoff |
| `429 Too Many Requests` | Transiente | Retenta com backoff |
| `500/502/503/504` | Transiente | Retenta com backoff |
| `400 Bad Request` | Permanente | DLQ direto |
| `401 Unauthorized` | Permanente | DLQ direto |
| `403 Forbidden` | Permanente | DLQ direto |
| `422 Unprocessable` | Permanente | DLQ direto |

**Confundir os dois é desastre:**
- Tratar 401 como transiente = loop infinito (sua chave está errada, retentar não vai mudar).
- Tratar timeout como permanente = perde mensagem por hiccup de rede.

<Aviso variante="dica" titulo="Antes de tudo, o que é 'backoff', 'jitter' e 'thundering herd'?">
- **Backoff exponencial** = "esperar cada vez mais entre retentativas". Ex: 1s, 2s, 4s, 8s, 16s. Dá tempo do problema externo se resolver.
- **Jitter** = "adicionar variação aleatória ao tempo de espera". Em vez de esperar exatamente 2s, espera entre 1.5s e 2.5s.
- **Thundering herd** = "manada estrondosa". Quando 1.000 clientes erram exatamente na mesma hora E todos esperam exatamente o mesmo tempo de backoff, eles retentam exatamente JUNTOS, derrubando o servidor de novo. Jitter dessincroniza.
</Aviso>

E o backoff precisa ter **jitter** (variação aleatória). Sem jitter, mil clientes errando na mesma hora retentam exatamente juntos — o famoso **thundering herd**.

### 1.3 Debouncer (consolidação de mensagens)

Usuário em chat raramente manda 1 mensagem completa. Manda 4 fragmentos em 3 segundos:

```
"Oi"
"Pode me ajudar?"
"Meu pedido"
"não chegou"
```

Sem debouncer: 4 turnos do agente, 4 respostas confusas, gasto 4×.
Com debouncer: aguarda **800ms de silêncio**, consolida tudo em 1 input, agente processa 1×.

<Aviso variante="dica" titulo="Em outras palavras...">
É o mesmo conceito da busca do Google: você digita "ja", "jam", "jama", "jamais"... mas o Google não busca a cada tecla — espera você parar de digitar por uns 300ms e BUSCA UMA VEZ. Senão seria 4 buscas inúteis. Debouncer é exatamente isso.
</Aviso>

## 6. Lab B — Webhook com HMAC

<Aviso variante="atencao" titulo="📖 História real — Por que você está fazendo isto">
**Novembro 2025.** Renato lançou bot de WhatsApp pra atendimento de pizzaria. Webhook recebia mensagens do cliente, agente respondia, ele consumia API da Meta. Funcionou nos testes.

Em produção, **atacante achou o endpoint** (não era difícil — domínio público) e descobriu que ele aceitava QUALQUER POST. Mandou requisições falsas se passando por Meta, simulando mensagens de usuários inexistentes.

Bot processou. Respondeu. Cada resposta chamava a API real da Meta pra enviar mensagem. **4.700 mensagens automáticas pra números aleatórios em 12 minutos.**

R$ 1.200 em SMS cobrados + **conta WhatsApp Business suspensa por 30 dias por padrão suspeito**. Pizzaria perdeu auge do mês.

Causa: faltava UMA verificação de HMAC-SHA256 (10 linhas de código).
</Aviso>

### 6.1 O que você vai conquistar

Função `verificarAssinatura()` em `src/sprint3/webhook.ts` que valida HMAC-SHA256 **em tempo constante** (resistente a timing attacks).

### 6.2 O contrato

<Diagrama legenda="Fluxo de verificação HMAC">
{`flowchart LR
    A[Provedor manda<br/>POST + signature header] --> B[Você recalcula HMAC<br/>com chave secreta]
    B --> C{timingSafeEqual<br/>signature vs calculado}
    C -->|igual| D[200 OK<br/>enfileira]
    C -->|diferente| E[401 Unauthorized]`}
</Diagrama>

<Aviso variante="dica" titulo="Antes de tudo, o que é 'timing attack'?">
**Timing attack** = ataque de tempo. Atacante mede MILISSEGUNDOS da resposta do servidor pra descobrir senhas caractere por caractere.

Como? Comparar strings com `===` é "preguiçoso": para no primeiro caractere errado. Se sua senha começa com "abc" e atacante tenta "axc", o `===` falha no 2º caractere (rápido). Se ele tenta "abd", falha no 3º caractere (um pouquinho mais demorado).

Medindo essa diferença microscópica, atacante adivinha a senha caractere por caractere. **Solução**: `timingSafeEqual` — compara TODOS os caracteres sempre, em tempo constante. Não vaza informação.
</Aviso>

## 7. Lab C — Fila com retry inteligente

<Aviso variante="atencao" titulo="📖 História real — Por que você está fazendo isto">
**Black Friday 2025, sexta 18h47.** Tatiana, eng. de pagamentos numa rede de marketplace, tinha integração com gateway de pagamento. Quando dava `503` (instabilidade temporária do gateway), o código retentava SEM backoff — só `setTimeout(50ms, retry)`.

Gateway caiu por **15 minutos**. Sistema chamou a API **47.000 vezes** nesse intervalo.

Banco do cliente detectou: **47k chamadas idênticas em sequência = comportamento de fraude.** Bloqueou a conta automaticamente. App offline por **6 horas** no pico de Black Friday.

Prejuízo estimado: **R$ 380 mil em vendas perdidas.**

Solução: retry com backoff exponencial (1s, 2s, 4s, 8s) + jitter aleatório de ±25%. Reduziria as 47k chamadas pra ~15. Você vai implementar isso hoje.
</Aviso>

### 7.1 O que você vai conquistar

Três funções em `src/sprint3/queue.ts`:
- `classificarErro(status)` — transiente ou permanente?
- `calcularBackoff(tentativa, cfg)` — exponencial com jitter
- `tentar(executor, cfg)` — loop com retry orquestrado

### 7.2 Por que isto importa

Em produção, ~5% das chamadas externas falham. Sem retry inteligente, você perde 5% do tráfego. Com retry burro, você multiplica custos. Com retry **inteligente**, você só retenta o que pode dar certo e descarta o resto.

### 7.3 Seu pedido ao agente

<PedidoAoAgente titulo="Lab C — Queue + Retry">
{`Implementar src/sprint3/queue.ts (esqueleto + tipos prontos).

classificarErro(httpStatus: number): "transiente" | "permanente"
- TRANSIENTES = [408, 429, 500, 502, 503, 504]
- PERMANENTES = [400, 401, 403, 404, 405, 422]
- Status desconhecido: trata como "permanente" (não retenta cegamente)

calcularBackoff(tentativa, cfg): number
- Exponencial: cfg.baseMs * 2^(tentativa-1), com Math.min para respeitar cfg.capMs
- Adiciona jitter ±25% (Math.random()*2-1 multiplicado por 25% do valor)

tentar(executor, cfg): Promise<{ ok, tentativas, ultimoStatus? }>
- Loop de 1 até cfg.maxTentativas:
  - Chama executor()

  - permanente → return { ok: false, tentativas, ultimoStatus } (NÃO retenta)
  - transiente E não é última tentativa → await setTimeout(calcularBackoff) e segue loop
  - transiente E última tentativa → return { ok: false, ... }

Restrições:
- TypeScript estrito.
- Sem deps externas.
- Comentários em português.

## 8. Lab D — Debouncer de mensagens

<Aviso variante="atencao" titulo="📖 História real — Por que você está fazendo isto">
**Dezembro 2025.** Igor lançou chatbot de atendimento numa loja online. Funcionava bem nos testes (mensagens completas, longas).

Em produção, **usuário típico de WhatsApp não escreve assim**. Manda 4-5 mensagens fragmentadas por turno:
- "Oi" [enter] "Pode me ajudar?" [enter] "Meu pedido" [enter] "número 4827" [enter] "ainda não chegou"

**Bot processou cada fragmento como turno separado.** 5 chamadas pro Claude por turno. 5x mais tokens. Resposta confusa (cada fragmento gerava uma resposta parcial: "Oi! Como posso ajudar?", "Claro!", "Você quer ajuda com o pedido?", "Qual o número?", "Vou verificar.").

Custo: **R$ 8 mil/mês a mais em tokens** + experiência ruim. Cliente reclamava "bot está louco, fica respondendo várias vezes".

Solução: debouncer de 800ms. Espera o usuário PARAR de digitar antes de processar. **Custo caiu pra R$ 1.6k/mês (-80%) e qualidade subiu.**
</Aviso>

Função `criarDebouncer(janelaMs)` em `src/sprint3/debouncer.ts` que consolida múltiplas mensagens rápidas de um mesmo usuário em UM batch.
